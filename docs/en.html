01 / The idea

Use what we have.
Differently.

The hypothesis: organising voluntary contributions around connectivity, trust and user comfort could make certain AI workloads accessible on existing computers.

Distributed inference already exists. Petals, exo and Prima.cpp are direct prior art. This project proposes an architecture and a user journey to test; it does not claim to have invented the principle. [1] [2] [3]

01

A contribution you control

Each participant chooses a memory and compute budget. The future agent must reduce or stop its contribution when the owner needs the machine.

02

Keep work close to resources

Computers with fast connections form groups. Across groups, favour independent tasks and infrequent transfers.

03

Prove value in a small pilot

Compare one computer with two or three. Measure time, quality, memory, failures and energy before scaling up.

Adding gigabytes does not turn them into one graphics card. Internet links add latency, computers differ and participants can leave. Work placement matters as much as the amount of memory. Read the detailed proposal

What about DNA, light and recovered heat?

DNA storage, including storage in living cells, has been demonstrated in published experiments. This does not establish working memory directly usable by a PC-based LLM. Glass addresses a different archival need. Analog in-memory computing and photonics are distinct hardware directions. [10] [11] [12] [13] [14] [15] [16] [17] [18] [31]

Qarnot and heata illustrate heat reuse. This inspires useful placement of computation, without demonstrating energy savings for our system. The approach proposed here starts with a pilot using existing computers. [8] [9]

02 / Architecture

Simple to join.
Careful to build.

A mesh does not mean every computer constantly talks to every other computer. Small groups execute tasks; discovery services and, when needed, relays help them find and reach each other.

  1. Install and join a group

    A signed app, an invitation, then approval of authorised computers. This graphical onboarding still needs to be built.

  2. Choose a contribution

    20% is an adjustable starting point. Show an actual budget, a comfort reserve and a stop button.

  3. Discover and test connections

    Local discovery can use mDNS. On the internet: rendezvous, NAT traversal and a relay if direct connectivity fails. [35] [36] [37]

  4. Check before starting

    Check the engine, model, budgets and authentication. Transport encryption does not hide data from a computer that must process it. [1] [33]

What could your contribution be?

An editable example. This calculation does not access your computer or allocate any memory.

7.2 GBTheoretical contribution cap

Formula: max(0, min(installed memory × percentage, available memory − reserve)). Decimal GB. Weights, caches, buffers and margins must all fit within this budget. Calculation source

Does it need an external server?

An initial group can operate on a local network. Across homes, some routers prevent direct connections: an accessible rendezvous or relay service may be needed. Volunteers or a hosting provider can operate it. [35] [36] [37] [38]

What about a blockchain?

It may be studied for contribution accounting. Communication required by computation remains off-chain. A blockchain does not remove latency, the need to verify work or privacy concerns. [6] [7]

03 / What the calculations say

Visible assumptions.
Reproducible results.

Simulation — not a hardware benchmark

Four scripts and their JSON outputs are published. The queue simulation covers 8 scenarios and 160,000 requests. Inference times are assumed; no actual GPU or model was measured in it. Method and results

Calculated nominal service times, excluding queueing
Modelled scenarioAssumed connectionNominal time / response
1 computerLocal compute6.32 s
4 computers on a LAN1 Gbit/s · 0.5 ms one-way6.56 s
4 computers over the internet100 Mbit/s · 20 ms one-way12.57 s

Assumptions: 512 input tokens, 64 output tokens; weights already loaded; prefill and first-token compute fixed at 1.28 s, then 63 × 80 ms compute. Network cost added; no batching or overlap. These three numbers are nominal service times, excluding queueing, variability and failure recovery.

In this model, distributing one request over the internet slows it down. Potential value lies in hosting certain models or serving multiple independent tasks. This still needs real-world measurement, including electricity use.

05 / Next steps

From the proposal
to the first real group.

The next useful goal: demonstrate a reproducible use case on two or three computers. A worldwide event will be a collective validation step after the pilot has been built and tested.

  1. 01
    Assemble the first group

    Identify 2 or 3 computers, their operating systems and connections. Choose a model, tasks and comparable success criteria.

    Next technical step
  2. 02
    Build the pilot and choose a licence

    Integrate an engine, discovery, authentication, quotas and recovery. Have the code reviewed and decide on a redistribution licence.

    Development required
  3. 03
    Measure on real computers

    Compare a single computer with the group, then test failures, response quality and electricity use.

    Measurements pending
  4. 04
    Test before the worldwide event

    Start on a local network, then 2 or 3 internet locations, a beta and a rehearsal. Only then set a UTC date and time.
